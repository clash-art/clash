# Project generation and editing

Creative skills provide the recipe; this skill owns Project execution. Apply
their prompts, reference roles, and review methods through the live Clash
contracts below. Names such as `--ref` in an upstream recipe describe an input
role, not a Clash argument. Preserve the conversation's provider/model choices
and authorization. Prefer a bundled Clash adaptation when available; do not
import its upstream backend discovery, setup wizard, or fixed confirmation
steps into the Project workflow. A failed required reference input remains a
failure to repair or report, not permission to discard the reference.

In a Clash project, generated or edited media is product state: the request,
background run, immutable output, and Canvas relationship must remain visible
to Clash. Use the `clash_generators` dispatcher for Project media generation
instead of calling a global `imagegen`, `image_gen`, video-generation, or other
standalone media tool. A global generator may be an implementation detail used
inside a Clash plugin, but the agent-facing turn must enter through Clash so
the output is persisted as a Project Asset rather than returned as an orphaned
file.

Use the live Generator contracts rather than guessing a provider-specific
payload:

For Model-based generation, use the `clash.model-generation` definition
for the output kind (`image`, `video`, `audio`, `model`, or `text`). Its revision state
contains `modelId`, `prompt`, and `params`; Model Cards own the supported inputs
and parameter values. Hilo and other Providers are execution routes, not separate
Generator definitions. When the user specifies a Provider, resolve its configured
account and pass `providerAccountId` in the Action submission input. Keep it out
of revision state and `params`. Read the live definition for exact input ports.

For text explicitly generated by a configured local agent (the former
`local-acp` executor), use `clash.agent-text` / `text` and its `generate` Action
through the same Generator APIs. Its state contains `prompt` and optional
`agentId`, `modelId`, and `systemPrompt`; here `modelId` selects the harness's
session model. Read the live Definition rather than treating `local-acp` as a
Model Card or Provider account. The output is an exact text Document revision,
read through the same Assets operation below. Its shipped Agent Text Action Card places this same Generator on Canvas;
read the live Card mapping when requesting placement.

When a Model input is an existing generated text Document, pass its exact
Output Commit asset reference (`kind: "document"`, `documentAssetId`, and
`revisionId`) through the definition's `text` input slot. Preserve that revision
when assembling the next Generator; a later Document head is a different input.
To read a committed text result, call `clash_assets` with operation
`document_revision_get` and the returned `documentAssetId` and `revisionId`.
The CLI equivalent is `clash assets documents get <documentAssetId> --revision <revisionId>`.
Both read the exact body and its provenance without creating a Canvas text copy.

1. Discover the matching definition with `definitions_list` and read the exact
   one with `definition_get` when it is not already known.
2. Create or read the Project Generator with `create` or `get`, preserving its
   returned Generator and Revision identities.
3. Submit the requested Action against that exact Revision with
   `action_run_submit`. Submission starts a background task; it is not proof of
   a finished asset.
4. Poll the returned Action Run with `action_run_get` until it reaches a
   terminal state, then read each persisted output through
   `output_commit_get`.
5. Use `clash_assets` or `clash_canvas` only for the next product operation,
   such as reading the committed Asset or placing/connecting it on Canvas.

The CLI exposes the same sequence: `generators definitions`, `generators definition <pluginId> <definitionId>`, `generators create`, `generators get <generatorId>`, `generators runs submit <generatorId> <actionId>`, `generators runs get <actionRunId>`, and `generators runs output <actionRunId> <outputSlot>`.
Before writing an unfamiliar `--input` payload, use `generators contract create`,
`generators contract advance`, or `generators contract submit` for the shared
request JSON Schema. Definition state/input schemas and Model Cards provide the
remaining model-specific details. Contract disclosure needs no project setup.

Canvas is a placement of the same Generator state. When editing an existing
Model card, read its `generatorId` and use that Generator; do not create a second
Generator for the same card. A new Generator can include `placement` to create
its Canvas card atomically. To copy a placed draft, preserve `forkedFrom` and
specify `placement.sourceNodeId`; the Host validates the source and projects
retained media inputs and copy lineage. Canvas reads/edits and the Generator
API are views and operations on these same facts, not separate generation engines.

If a required Generator definition or action is unavailable, report the Clash
capability gap. Do not silently fall back to a global media skill, write a
lookalike file, or claim that an external tool result belongs to the Project.
